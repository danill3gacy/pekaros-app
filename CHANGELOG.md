# История версий КофейняОС

## 5.0.0 — продукт стал кофейней

Продукт целиком перебран под кофейню. Это не смена вывески: у кофейни другой
центр тяжести денег, и почти все расчёты пришлось строить заново. Пекарное ядро
не выброшено — самая проверенная его часть сохранена и перенацелена.

### Сменился предмет: витрина вместо выпечки

- **Напиток кончиться не может.** Латте делается на заказ, поэтому весь движок
  «спрос ≠ продажи» теперь применяется ТОЛЬКО к витрине — еде с конечным
  запасом. Раньше, попади туда напитки, система «обнаруживала» бы
  распроданность латте каждый вечер после закрытия.
- **План выпечки → заказ витрины.** Логика сохранена целиком: восстановление
  усечённого спроса по условному матожиданию, усадка по дню недели, запас из
  целевого уровня сервиса, приоритет ручной правки владельца.
- **Упущенная выручка стала дороже.** В пекарне не хватило булки — потеряли
  продажу булки. В кофейне не хватило завтрака — гость взял только кофе, а
  назавтра пошёл завтракать туда, где витрина не пустая, и кофе взял уже там.

### Появилось то, от чего пекарная версия отказывалась осознанно

Прошлая версия не считала себестоимость, и это было правильное решение: между
мукой и багетом стоят тесто, расстойка и рука пекаря — расход из чеков не
восстановить.

В кофейне между зерном и латте не стоит ничего. Рецепт постоянен: 18 г зерна,
200 мл молока, стакан, крышка. Поэтому:

- **Себестоимость и маржа каждой позиции** считаются точно (`costing.py`).
- **Рецептура поставляется готовой** (`reference.py`): владелец вводит только
  цены, а не заполняет тех.карты. Тех.карты никто не заполняет.
- **Разбор меню по деньгам**: звёзды, рабочие лошадки, загадки, балласт —
  сравнение с медианой собственного меню, а не с отраслевым нормативом.
- **Экономика молока отдельно.** Наценку за растительное ставят один раз, а
  закупка дорожает. Продукт показывает, покрывает она разницу или нет.
- **Точный расход и заявка поставщику** (`supply.py`): не «закажите зерно», а
  «27 кг зерна, 58 л молока; молоко — каждые 3 дня, дольше не хранится».

### Новое, чего в пекарне не было и быть не могло

- **Разбор позиции чека** (`menu.py`). «Айс латте 450 на овсяном + сироп» —
  это не уникальный товар, а латте размера L на овсяном молоке. Без разбора
  каталог кофейни рассыпается на сотни имён, и ни расход, ни маржа, ни
  attach-rate не считаются.
- **Attach-rate «кофе + еда»** — главный рычаг среднего чека: напиток берут и
  так, еду добавляют, только если предложили. Отдельно показан разрыв между
  утром и днём: к обеду витрина обычно уже не работает.
- **Пропускная способность смены** (`staffing.py`). Кофейня упирается не в
  запас, а в руки.
- **Регламент обслуживания.** Сбитая помолка уводит дозу на 2–3 г с чашки —
  это десятая часть расхода зерна; забитый фильтр убивает бойлер.
- **Списания разделены**: витрина по ценнику (непроданная выручка), вылитое
  молоко по себестоимости (прямой расход). Складывать их в одну сумму значило
  бы сравнить разные вещи. Вылитого молока нет вообще нигде, кроме этой строки.
- **Импорт понимает кофейные выгрузки**: модификаторы и размер из отдельных
  колонок, сотрудник, карта гостя, тип заказа (Poster, iiko, r_keeper, Эвотор,
  Quick Resto). Модификатор приклеивается к названию перед разбором.
- **`rescan`** — пересборка разбора всей истории после правки каталога. Раньше
  исправление действовало только на новые чеки.

### Три настоящих дефекта, найденных при переборе

- **Обновление ломало рабочую базу.** Индекс по новой колонке создавался в том
  же скрипте, что и таблицы: на базе, которая обновляется с пекарной версии,
  `CREATE TABLE IF NOT EXISTS` колонку не добавляет, а `CREATE INDEX ... (base)`
  падает с «no such column». Индексы вынесены после миграций.
- **Заявка раздувала запас.** Срок поставки прибавлялся к объёму заказа каждый
  цикл. Через месяц под стойкой стоял бы месячный запас зерна на деньги из
  оборота. Срок поставки влияет на то, КОГДА заказать, а не СКОЛЬКО.
- **Гарантированный стокаут молока.** Скоропорт заказывался на 3 дня, а цикл
  заявки был недельный — с четверга кофейня оставалась без молока. Теперь у
  такой позиции свой цикл заказа, и продукт говорит об этом вслух. Дефект нашёл
  симулятор, а не человек: `--supply` показал 63 дня из 69 без молока.

### Продукт по-прежнему не выдумывает

Главный принцип прошлой версии сохранён и распространён на новые разделы.

- **Неизвестная цена даёт «не посчитано», а не «маржа 100%».** Пока владелец не
  назвал закупочную цену витрины, себестоимость — `None`, а не ноль. Типовые
  цены помечаются как типовые.
- **Оценки подписаны как оценки.** Первая версия attach-rate обещала +149 тыс.
  ₽/мес, распространяя лучший час на весь день. Такую цифру нельзя опровергнуть,
  поэтому она ничего не стоит; теперь потенциал считается по собственной медиане
  часов и выходит на порядок скромнее.
- **Сценарий второго бариста стал измерением.** Раньше он опирался на допущение
  «спрос в очереди есть». Теперь продукт проверяет это по распределению: если
  час просто популярный, число чашек в нём гуляет день ото дня; если рук не
  хватает — распределение срезано сверху. Без подтверждения упора в потолок
  цифра не показывается вовсе.
- **Ровный день больше не выглядит сплошным пиком.** Час считается загруженным,
  только если он выше медианного минимум в 1,4 раза.
- **Возвращаемость гостей и работа бариста** показываются, только если касса
  передаёт гостя и сотрудника. Иначе раздел честно говорит, что не знает.
- **Система работает без ежедневного ручного ввода.** Проверено тестом и
  отдельной строкой в симуляции: без единого списания заказ витрины не
  разъезжается. Продукт, который держится на ручном вводе, умирает вместе с
  бариста, которого научили.

### Сплошной аудит после пивота: ещё 8 дефектов

Продукт прогнан по вырожденным базам (пустая, один чек, только напитки, только
витрина, только служебные позиции, выгрузка без времени, нули и минусы в
ценах), по кривым выгрузкам, по вводу персонала и по одновременной работе бота,
автозагрузки и сайта.

- **Раздел «Маржа» показывал не ту выручку.** Там стояла сумма только по
  напиткам и витрине, а подписана она была как выручка заведения — на несколько
  процентов меньше кассовой. Владелец сверил бы с кассой и решил, что система
  считает неверно. Теперь показываются обе цифры: выручка заведения целиком и
  доля, по которой маржа действительно посчитана.
- **Неоднозначное списание молча уходило не туда.** «Списание круассан 3» при
  двух круассанах в витрине выбирало один из них — и не тот. Последствие хуже,
  чем кажется: списание гасит признак распроданности, поэтому по настоящему
  кончившемуся круассану упущенная выручка переставала считаться, а по
  невиновному росли «остатки». Теперь система переспрашивает. То же для
  остатков, цен и правки каталога.
- **Раздел «Молоко» падал целиком**, если хоть у одной позиции была нулевая
  цена (акция, служебная строка кассы): неопределённый фудкост доходил до
  форматирования как `None`. Теперь в такой ячейке прочерк.
- **Регламент обслуживания не понимал падежей.** «Сделал калибровку» не
  находило «Калибровка помола», и раздел выглядел неработающим. Сопоставление
  идёт по основам слов.
- **«Цена зерно -500» уходило в раздел заявки**, и владелец был уверен, что
  цену задал. Теперь отказ с объяснением.
- **Опечатка в инвентаризации принималась без проверки**: «остаток зерно
  99999999» давало «хватит на 71 миллион дней» и глушило заявку целиком.
- **Заполнители в колонке модификаторов плодили мнимые позиции.** Кассы кладут
  в пустую колонку «-» или «нет»; приклеенные к названию, они превращали один
  латте в три разных товара в каталоге и в дедупликации.
- **Подтверждение остатка не называло единицу измерения** — «Остаток Зерно
  кофе: 3» не отвечало на вопрос «три чего».

Отдельно проверено и оказалось в порядке: кэши видят правку цен, каталога,
новый чек и новое списание; веб отвергает кривые payload; заявка не заказывает
меньше нужного; чеки в 00:00 и 23:59 попадают в свой день; заказ витрины на
каталоге в 400 позиций считается мгновенно; 120 тыс. строк импортируются за
1,6 с; бот, автозагрузка и сайт пишут в базу одновременно без конфликтов.
Ответы бота проверены на лимит Telegram в 4096 символов и на парность разметки.
На занятую базу бот теперь отвечает «идёт загрузка выгрузки, повторите через
минуту» вместо «что-то пошло не так».

### Проверка

- Симулятор перенацелен: независимая модель спроса (обеденный пик вместо
  утреннего), четыре стратегии витрины и новый режим `--supply`, проверяющий,
  что заявка не даёт встать без зерна и молока.
- Точка отсчёта честнее: сравнение идёт не с собственной прошлой версией,
  которой ни у кого нет, а с **табличкой со средним за две недели** — тем, как
  реально считает большинство кофеен. Она проигрывает даже «чутью владельца».
- 144 теста: разбор меню, себестоимость, витрина, расход и заявка, смена,
  attach-rate, списания, импорт шести форматов выгрузок, доступ и здоровье,
  честность интерфейса.

## 4.2.0 — продукт перестал выдумывать

Главный дефект прошлых версий был не в расчётах, а в честности: интерфейс
показывал цифры и статусы, за которыми ничего не стояло, а кнопки делали вид,
что работают. Владелец принимал это за правду. Исправлен 31 дефект.

### Выдуманное — убрано

- **Раздел «Подключения»** («Эвотор подключено», «1 240 чеков», «63 позиции»)
  показывался даже при выключенной синхронизации. Удалён.
- **Раздел «Смены»** с несуществующими сотрудниками, их графиками и
  рекомендациями. Таблицы смен в базе нет и не было. Удалён.
- **Три кнопки-пустышки** на дашборде: «Утвердить и отправить пекарю»,
  «Отправить поставщику», «Применить» к смене — рисовали успех без единого
  запроса к серверу.
- **Кнопки −/+ в плане выпечки** меняли число только на экране: пекарь получал
  исходный план, а владелец был уверен, что поправил его.
- **`dashboard.html`** — 60 КБ мёртвого макета, который сервер никогда не
  отдавал и который не делал ни одного запроса. Удалён.
- **Кнопка «Утвердить и отправить пекарю» в боте** отвечала «отправлен пекарю»,
  ничего не отправляя.

### Стало настоящим

- Правка партии сохраняется в базу (`POST /api/plan/adjust`) и уходит пекарю
  вместе с планом; в плане появляется пометка «вы поправили вручную».
- «Утвердить» (`POST /api/plan/approve`) реально отправляет план в Telegram и
  честно сообщает результат — включая «получатели не настроены».
- **Упущенная выручка** — главная ценность продукта — теперь видна на
  дашборде. Раньше она считалась, приходила в API и нигде не отображалась.
- Дашборд переписан целиком: ни одного захардкоженного числа, статуса или
  имени. Пустая база даёт «данных пока нет», а не бодрые нули.

### Система признаёт, чего она не знает

- **Выгрузка без времени продажи** больше не даёт молча «пик продаж 0:00» и
  «упущенная выручка 0 ₽»: импорт, бот, статус и дашборд предупреждают, что
  на таких данных эти показатели не считаются.
- **Выгрузка без номера чека** предупреждает, что состав чеков не восстановить
  и средний чек недостоверен. Раньше признак вычислялся и никуда не выводился.
- **Пустая база** выдаёт тревогу, а не сводку «Выручка 0 ₽».

### Безопасность

- **Бот больше не пускает любого**, пока список допущенных пуст. Раньше одна
  незаполненная строка в `.env` делала выручку и планы публичными для всех,
  кто нашёл бота в поиске. Теперь работает только `/start`, который показывает
  человеку его chat_id.
- `validate()` предупреждает и об открытом доступе к боту, и об отсутствии
  пароля на сайте.
- Службы systemd работают от отдельного пользователя, а не от root, с базовой
  изоляцией; `install.sh` ставит на `.env` права 600 (там токен и пароль).

### Данные и расчёты

- **9 из 22 реальных названий выпечки** уходили в «Прочее» и навсегда выпадали
  из плана (кулебяка, расстегай, шарлотка, пирог, панеттоне, гриссини,
  крендель, чак-чак). Словари категорий расширены — распознаются все 22.
- **Каталог теперь можно править:** «печём фокачча», «не печём кофе»,
  «каталог». Раньше флаг ставился один раз при импорте и исправить его было
  нечем.
- **Одна списанная булка больше не отменяет распроданность за весь день** —
  введён порог (2 шт или 3% дневных продаж).
- **Единый часовой пояс** для бота, аналитики, списаний и копий: на сервере в
  UTC «сегодня» расходилось на три часа.
- Оценка спроса **взвешивается по свежести** (период полураспада 21 день):
  без этого план отставал от тренда и на независимой модели спроса проигрывал
  даже владельцу, который просто смотрит на вчера.
- `demand_stats` кэшируется: один `/api/summary` считал её трижды.
- Миграции проверяют схему через `PRAGMA table_info`, а не глушат любые
  исключения через `except: pass`.
- Из `.env` убраны `COST_SHARE`, `SALVAGE_SHARE` и упоминание команды
  «себестоимость …», которых в коде нет с версии 4.1.0.
- Тревоги о поломках больше не повторяются каждые 6 часов: не чаще раза в
  сутки, и отдельное сообщение, когда всё починилось.

### Проверяемость

- **Симулятор получил независимую модель спроса.** Пока он брал профиль часов
  и дней недели у генератора демо-данных, он проверял алгоритм на том же мире,
  из которого этот алгоритм вырос, и опровергнуть продукт не мог в принципе.
- На честной модели заявленная в README выгода **не подтвердилась**: вместо
  «+28,5 тыс. ₽/мес» получается около +3 тыс. с разбросом от −2 до +12. README
  исправлен. Прежняя версия 3.2 при этом стоит владельцу −100 тыс. ₽/мес, то
  есть текущая версия закрыла настоящую яму, а не создала выгоду из воздуха.
- Три теста были декоративными и теперь проверяют дело: тест о README не
  выполнял тело условия никогда; тест о смене запрещал строку, которая
  дословно лежала в дашборде; тест доступа не проверял главный случай —
  пустой список допущенных.
- Тестов: 79 → 90.

## 4.1.1 — сплошной аудит: 30 исправленных дефектов

Продукт проверялся не «работает ли код», а «не врёт ли он владельцу и не теряет
ли его данные». Нашлось три класса проблем: потеря денег при импорте, молчаливое
искажение главных метрик и мелкие поломки интерфейса. Все правки закрыты
тестами (79 против 57 до аудита).

### Импорт чеков: терялась и задваивалась выручка

- **Типовая выгрузка 1С/Эвотора грузилась с нулевой выручкой.** Заголовки
  «Кол-во товара», «Цена товара», «Сумма товара» опознавались как наименование
  (из-за слова «товар»), колонки денег не находились вовсе — и импорт
  рапортовал об успехе. Теперь колонка определяется по позиции ключевого слова
  в заголовке, а не по порядку списка.
- **Сбой посреди импорта уничтожал всю историю продаж.** Очистка базы
  коммитилась отдельно от записи, откатывать было нечего. Теперь очистка и
  запись — одна транзакция с откатом.
- **Повторная выгрузка того же чека роняла импорт** (`ValueError` в сверке
  позиций), а в режиме автозагрузки файл уезжал в карантин.
- **Цена «0» при заполненной сумме обнуляла позицию** — это штатный формат ОФД
  для скидок и округлений. Теперь цена берётся из суммы.
- **Два разных чека с одним номером в один день склеивались** (посменная
  нумерация кассы), выручка второго терялась. При этом одна и та же выгрузка,
  пришедшая с временем и без него, больше не грузится дважды.
- **Исправления от кассы применяются**, а не теряются: уточнённое количество
  обновляет чек; схлопнутые строки не задваивают выручку; частичная выгрузка
  никогда не удаляет уже загруженные позиции.
- Разделитель CSV теперь определяется по строке заголовка и знает табуляцию;
  понимается unix-время; «cash»/«card» из API больше не считаются безналом;
  обрезанные строки попадают в счётчик битых, а не в базу с нулевой ценой.

### Метрики: молча показывали не то

- **Возвраты обнуляли упущенную выручку.** Час возврата считался «часом
  последней продажи», распроданность переставала определяться — и по самым
  ходовым позициям главная метрика продукта показывала ноль.
- **«В месяц» занижалось на 20%,** когда истории меньше окна расчёта.
- **Перепёк новинки не замечался:** списания усреднялись по всему окну, а
  продажи — по дням жизни позиции. Теперь знаменатель общий.
- **План выпечки мог предложить «испечь 33 пакета-майки»** — добавлен фильтр
  служебных позиций, не зависящий от флага в каталоге.
- Снятая с производства позиция больше не остаётся в рекомендациях из кэша.
- Крупный возврат больше не даёт долей вида «Хлеб 120%».

### Интерфейс

- **Мусорные списания больше не портят данные:** «списание с 3» записывало
  3 багета, «списание багет 999999» — почти 90 млн ₽, а по такому дню система
  переставала видеть распродажи. Добавлена проверка названия и количества.
- «списание багет 5 штук» записывается (раньше молча показывался отчёт, и
  продавец был уверен, что списание внесено), а непонятный формат получает
  подсказку вместо отчёта за вчера.
- Названия товаров вида «Кофе 3_в_1» больше не ломают разметку сообщения.
- `/status` не подвешивает бота на время проверки связи с моделью.
- Нажатие кнопки в режиме заявки больше не отправляет поставщику текст
  «📈 Выручка».
- Маршрутизация: «прогноз» и «проверка кассы» попадают в свои разделы, «печь
  сломалась» больше не открывает план выпечки, «сколько списали» распознаётся.
- Ротация резервных копий больше не удаляет только что созданную копию (и не
  падает следом), а демо-данные не стирают ручные списания персонала.
- Диагностика ИИ не выдаёт «модель готова», когда установлена соседняя версия,
  и не советует `ollama pull` при ошибке лимита запросов.

## 4.1.0 — себестоимость убрана из системы

Владельцу маленькой пекарни не нужно знать и вводить свою себестоимость — а
раньше от неё зависели и план выпечки, и все денежные отчёты. Убрали её
полностью: система больше нигде не считает и не хранит себестоимость сырья.

- **План выпечки** теперь строится на фиксированном целевом уровне сервиса
  (по умолчанию 70% спроса) вместо перцентиля из формулы газетчика по
  себестоимости. Поведение близко к прежнему на типичной пекарне, но без
  единой настройки.
- **Отчёт «Что зарабатывает» (маржа)** удалён целиком — вместе с командой
  `/marzha`, кнопкой и API-полем `margin`.
- **Списания** показываются в штуках и на сумму по ценникам (розничной цене);
  расчёт «реальной потери по себестоимости» убран.
- **Упущенная выручка** считается по полной цене (штуки × цена), а не по марже.
- Убраны настройки `COST_SHARE` и `SALVAGE_SHARE`, таблица `cost_config`,
  команда чата «себестоимость …» и отраслевые доли сырья по категориям.
- `tools/simulate.py` сохранён как бенчмарк: долю сырья он берёт как внешнее
  допущение (`--cost`) только для оценки прибыли, система её не использует.

## 4.0.0 — план выпечки начал зарабатывать деньги

Разбор с позиции владельца бизнеса, а не разработчика. Проверялось не «работает
ли код», а «приносит ли продукт деньги пекарне». Оказалось, что нет.

### Ядро: продукт терял деньги клиента

**План выпечки оптимизировал не ту величину.** Формула была
`план = спрос − 0.6 · списания`: система старалась снизить списания. Но в
пекарне потери несимметричны — непроданная булка стоит владельцу только сырьё
(~30% цены), а булка, которой не хватило, стоит всю маржу (~70%). Минимизируя
видимые списания, продукт увеличивал невидимую недопродажу, которая вдвое
дороже.

Замкнутая симуляция на одном и том же потоке покупателей
(`tools/simulate.py --days 120 --seeds 5`, сырьё 30%, среднее по 5 потокам):

| стратегия | валовая прибыль | к «чутью владельца» | фактический сервис |
|---|---|---|---|
| чутьё владельца (никакой системы) | 988 558 ₽/мес | — | 34% |
| ПекарьОС 3.2 | 932 426 ₽/мес | **−56 132 ₽** | 17% |
| ПекарьОС 4.0 | 1 017 080 ₽/мес | **+28 522 ₽** | 57% |

Прежняя версия была **хуже, чем не иметь системы вовсе**, и устойчиво: на всех
пяти потоках от −52 до −57 тыс. ₽/мес. Разница между 3.2 и 4.0 — около 85 тыс.
₽/мес на пекарне с оборотом 1,3 млн.

Где преимущество надёжно, а где нет (среднее и разброс по 5 потокам):

| сырьё, % цены | 4.0 к «чутью» | разброс |
|---|---|---|
| 25% | +41 017 ₽/мес | +34 107 … +44 733 |
| 30% | +28 522 ₽/мес | +22 680 … +32 329 |
| 35% | +18 037 ₽/мес | +13 627 … +21 219 |
| 45% | +1 644 ₽/мес | −649 … +3 564 — **шум, знак меняется** |

Честная формулировка: продукт надёжно зарабатывает при себестоимости сырья до
~35–40% цены. Это покрывает нормальную пекарню (25–35%), но не заведение с
дорогим сырьём — там выигрыш неотличим от нуля, и обещать его нельзя.

**Фактический уровень сервиса ниже целевого** (57% при цели 70%) и это не
скрывается: μ и σ оцениваются по урезанным продажам и потому смещены вниз.
Симулятор печатает фактический сервис отдельной колонкой, чтобы расхождение
было видно, а не пряталось за формулой.

**Что сделано.** План теперь считается как `средний спрос + z·сигма`, где `z`
соответствует уровню сервиса `(1 − доля_себестоимости) / (1 − доля_уценки)` —
классическая задача о газетчике. Вся денежная логика вынесена в новый модуль
`coffeeos/economics.py` с объяснением формул.

**Себестоимость стала настраиваемой** — по позиции, по категории и по пекарне,
прямо из чата: «себестоимость круассан 35». До настройки берутся отраслевые
значения по категориям. Это не косметика: от этого числа напрямую зависит
размер партии.

### Продажи ≠ спрос

**Система не отличала «продали 50, потому что столько хотели» от «продали 50,
потому что столько испекли».** Все прогнозы строились на урезанных данных и
воспроизводили вчерашний недопёк.

Теперь распроданность определяется **по чекам, без всякого ручного ввода**:
если позиция перестала продаваться задолго до закрытия, а покупатели ещё шли,
она кончилась. Проверка вероятностная (`(1 − доля вечернего трафика)^число
продаж < порога`), поэтому низкий спрос не путается с распроданностью. Спрос в
такие дни восстанавливается по условному матожиданию усечённого распределения,
поправка ограничена сверху.

**Снята зависимость от ручного ввода списаний.** Раньше единственным признаком
«не хватило» были списания, которые продавец должен вводить каждый вечер. При
текучести 4–5 месяцев это перестают делать через месяц, и продукт слепнет.
Теперь списания — уточнение, а не топливо: в симуляции вариант «продавец не
ввёл ни одного списания» даёт тот же результат (1 022 857 ₽ против 1 022 807 ₽).
Вечернее напоминание переписано на необязательное, это покрыто тестом.

### Новое: деньги, которых не видно в кассе

- **Упущенная выручка** (`/upusheno`, кнопка «💸») — сколько недополучено из-за
  того, что товар кончался, по позициям, с указанием часа. Ни касса, ни ОФД
  этого не показывают: они знают проданное, но не знают, сколько человек
  развернулось и ушло.
- **Что зарабатывает** (`/marzha`, кнопка «💰») — валовая прибыль по позициям.
  Топ по обороту и топ по деньгам — разные списки, и владелец малой пекарни не
  видит второй нигде.
- Утренняя сводка и экспресс-аудит перестроены вокруг этих денег.

### Исправления доверия

- **Ответ про смену был захардкожен.** «Пик спроса — 08:00 и 18:00, усильте
  вечернюю смену вторым продавцом с 16:00» выдавалось любой пекарне независимо
  от данных — при том, что рядом уже считался настоящий профиль по часам.
  Теперь пики, тихий час и нагруженные окна берутся из чеков; два пика
  разносятся по времени (иначе «08:00 и 09:00» — это один утренний пик).
- **README обещал функцию, которой нет в коде**: «задание остатков сырья из
  бота („остаток мука 40")». Обработчика не существует. Обещание убрано,
  добавлен тест, который не даст такому вернуться, и раздел «Чего продукт НЕ
  делает».
- **Списания показывались по розничным ценникам.** «Списано на 15 000 ₽» при
  реальной потере около 4 500 ₽ — завышение втрое. Это не безобидная
  неточность: именно она и подталкивает владельца резать партии. Теперь
  показываются обе цифры, реальная выделена.

### Демо-данные больше не вводят в заблуждение

Генератор моделировал пекарню с **бесконечным запасом**: продажи никогда не
упирались в выпечку, распроданностей не возникало вовсе. На таких данных задача
прогноза искусственно лёгкая, а главная ошибка — недопёк — не видна в принципе.

Теперь моделируется конечная партия: владелец печёт по своему чутью, реагируя
на остатки резче, чем на распроданность (как в жизни), товар кончается, часть
спроса уходит. Демо-пекарня даёт около 1,27 млн ₽/мес при списаниях ~12% партии
в штуках (≈3,7% выручки по себестоимости) — правдоподобные цифры.

### Проверяемость

- `tools/simulate.py` — сравнение стратегий на одном потоке покупателей, с
  усреднением по нескольким потокам (`--seeds`) и показом фактического уровня
  сервиса. Любое утверждение продукта про деньги перепроверяется одной командой.
- Тестов: **38 → 53**. Новые покрывают уровень сервиса, план выше среднего
  спроса, реакцию на дорогое сырьё, определение распроданности по чекам,
  приоритет списаний над эвристикой, работу без единого ручного ввода,
  разделение ценника и реальной потери, отсутствие хардкода в ответе про смену,
  настройку себестоимости из чата и честность README.

### Найдено независимым ревью и исправлено

Готовую 4.0 отдельно ломали на крайних случаях. Нашлось четыре реальных
дефекта — все закрыты и покрыты тестами:

- **Предохранитель на поправку спроса убивал сезонные позиции и новинки.**
  Средние по дню недели и общий потолок считались по разным знаменателям.
  Позиция «только по субботам» получала план 3 при спросе 10; новинка,
  проданная вчера в 40 штуках, получала план 1 — и не могла из этого выбраться
  никогда, потому что при партии в 1 штуку распроданность не фиксируется.
  Теперь дни считаются с момента появления позиции, а потолок сравнивается с
  тем же срезом сырых продаж.
- **Падение на возвратах.** При отрицательном среднем `mu ** 0.5` давало
  комплексное число и роняло `bake_plan`, а вместе с ним утреннюю сводку,
  дашборд и ассистента.
- **Ложные распроданности у «утренних» позиций.** Проверка исходила из того,
  что товар одинаково вероятен в любом чеке дня. Круассан, который продаётся
  только до 10 утра и никогда не кончается, помечался распроданным 40 дней из
  40, спрос завышался, а отчёт показывал 8 600 ₽/мес несуществующей упущенной
  выручки. Теперь позиция сравнивается сама с собой: день засчитывается,
  только если она кончилась минимум на два часа раньше своего обычного часа.
- **Две разные оценки одной величины в одном сообщении** — «за вчера» и «в
  среднем» считались по разным базам. Приведены к одной.

Плюс мелкое: сигма занижалась из-за неучтённых степеней свободы; уценка
учитывалась в отчёте о списаниях, но не в отчёте о марже; «в месяц» считалось
по 30 дням вместо фактических рабочих; окно списаний в плане не совпадало с
окном спроса.

## 3.2.0 — финальный аудит: регрессии и последние дефекты закрыты

Четвёртое независимое ревью проверяло в том числе регрессии от прошлых правок.
Найденное исправлено и покрыто тестами (38 тестов).

Критическое:
- **Определение кодировки ломалось на файлах больше 64 КБ.** Проверялся только
  первый кусок, и граница разрезала кириллический символ — файл признавался
  cp1251 и читался мусором. На проверке 40 из 40 реальных выгрузок (~200 КБ)
  не импортировались вовсе, уезжая в карантин без уведомления владельца.
  Теперь проверяется файл целиком: 20 из 20 больших файлов грузятся верно.
- **Один чек с датой из будущего обнулял весь продукт.** Сбитые часы кассы или
  тестовый чек с 2027 годом — и сводка, план выпечки и дашборд показывали
  «выручка 90 ₽, 1 чек», а самоконтроль молчал. Будущие даты больше не берутся
  за «последний день», а бот предупреждает о таких чеках.
- **Автосброс демо-данных мог стереть реальные данные клиента.** Удаление шло
  до разбора файла: посторонний CSV в папке автозагрузки очищал базу, и только
  потом возникала ошибка. Плюс стирались ручные списания персонала —
  единственные данные, которые вводят люди. Теперь чистка только после
  успешного разбора, а ручные списания сохраняются (метка источника).
- **Возврат, помеченный минусом только в колонке «Сумма»**, засчитывался как
  продажа (при наличии колонки «Цена» сумма не читалась вовсе).

Регрессии прошлых правок:
- **Строка скидки внутри чека порождала фантомный «чек возврата»** — средний
  чек занижался вдвое у пекарни с программой лояльности. Отдельным чеком
  считается только возврат по документу.
- **До-заполнение чека задваивало позицию** при уточнении цены или количества
  (корректировка кассира: 90 ₽ превращались в 270 ₽).
- **Кэш среза не замечал до-заполнения** — бот до конца дня отвечал по старым
  цифрам.
- **Профиль дней недели строился по одному наблюдению.** Одна ярмарка в среду
  при короткой истории — и план на все следующие среды утраивался (300 шт при
  спросе 129). Теперь нужно не меньше трёх наблюдений на день недели, разброс
  ограничен разумными рамками.

Безопасность и эксплуатация:
- **Поставщик имел полный доступ к аналитике** (выручка, аудит, касса). Теперь
  бот только отправляет ему заявки.
- **Лог не ротировался** — около 1 МБ в сутки, к третьему месяцу переполнение
  диска рядом с базой; в лог попадал токен бота. Включена ротация, служебные
  логи приглушены.
- **В поставке лежал рабочий токен бота** — удалён из шаблона настроек.
- Редактирование своего сообщения роняло обработчик.
- Опечатка в chat_id молча запирала владельца снаружи — теперь запуск
  прерывается с понятным объяснением.

## 3.1.0 — третий аудит: закрыты блокеры безопасности и потери денег

Независимое ревью нашло дефекты, которые проявились бы у первого же клиента.
Все исправлены и покрыты тестами (28 тестов).

Безопасность:
- **Бот был открыт любому пользователю Telegram.** Посторонний мог узнать
  выручку пекарни и записать ложное списание, испортив план выпечки. Теперь

- **Пароль сайта с русскими буквами не работал** (владелец не мог войти,

- Служебные страницы API (/docs) закрыты; при запуске сайта без пароля —
  предупреждение в лог.

Деньги и данные:
- **Возвраты не распознавались** при заголовке «Тип чека»/«Тип документа» —

  до-заполняется недостающими позициями.

- **Половина ассортимента уезжала в «Прочее»** и выпадала из плана выпечки
  (ватрушки, рогалики, плюшки, куличи, тарты, печенье, чизкейки…). Словарь
  категорий расширен под реальную пекарню.
- **«Сосиска в тесте» считалась служебной позицией** (ловилась на «тест») и

- **Одна старая запись о списании** завышала все партии на 10% навсегда:

- **План выпечки строился на коэффициентах демо-генератора.** Теперь профиль

## 3.0.0 — готовность к боевой эксплуатации

Доработки под то, что обязательно случится с реальными данными и при передаче
клиенту.

Корректность на реальных выгрузках:
- **Возвраты** (колонка «Тип операции» = Возврат либо отрицательные числа)
  теперь вычитаются из выручки, а не завышают её.
- **Служебные позиции кассы** — пакеты, скидки, доставка, сертификаты, тара —
  распознаются и НЕ попадают в план выпечки. Раньше система предлагала бы

- В план выпечки попадают только хлеб и выпечка; напитки и прочее — никогда.
- Импорт показывает, сколько учтено возвратов и служебных позиций.

Сохранность данных:
- **Автоматические резервные копии** базы каждую ночь (штатным механизмом
  SQLite, безопасно при активной записи), хранение последних 14 штук с ротацией.
  Команды `python -m coffeeos backup` и `backups`.

Безопасность:
- **Пароль на веб-дашборд** (WEB_USER/WEB_PASSWORD). Без него выручку пекарни
  видел любой, кто знает адрес сервера. Пароль генерируется при установке.

Установка и эксплуатация:
- **Скрипт установки `install.sh`**: ставит зависимости, создаёт окружение,
  готовит .env, прописывает абсолютный путь к базе, генерирует пароль сайта,
  создаёт службы systemd для автозапуска 24/7 и печатает оставшиеся шаги.
- Самоконтроль считает время в часовом поясе пекарни, а не сервера
  (иначе на сервере в UTC были бы ложные тревоги).
- В боте появилась отмена заявки поставщику («отмена») — раньше из этого
  режима нельзя было выйти.
- Комментарий в строке настройки .env больше не попадает в значение.

## 2.7.0 — второй полный аудит: критические исправления

Независимое ревью кода нашло блокеры, которые исказили бы реальные данные.
Все исправлены и покрыты тестами (19 тестов).

Критическое:
- **Загрузчик чеков переписан.** Раньше из многострочного чека импортировалась
  только ПЕРВАЯ позиция (остальные считались «дублями») — терялось до 65%
  выручки молча. Теперь позиции корректно группируются по чеку.
- **Дедуп по (дата + номер чека).** Раньше кассы, нумерующие чеки с 1 каждый
  день, теряли весь следующий день. Без номера чека — дедуп по содержимому,
  так что повторная загрузка файла больше не задваивает выручку.
- **Пустой номер чека** больше не роняет вставку и не теряет чеки.
- **Колонки «Дата» + «Время» отдельно** теперь распознаются (раньше молча
  импортировалось 0 строк, а файл уезжал в архив как «загруженный»).
- **План выпечки был завышен на ~48%** из-за неверной нормировки коэффициента
  дня недели — исправлено, отклонение 0%. «Недопродажа» определяется только
  при реальном учёте списаний.
- **Вопросы про списания писали мусор в базу** («покажи списания за 3 дня» →
  запись «за — 3 шт»), причём и через GET-запрос веб-API. Теперь запись только
  по строгой команде и только из Telegram; веб работает в режиме чтения.

Надёжность:
- SQLite переведён в режим WAL с таймаутом — бот, автозагрузка и сайт больше
  не блокируют друг друга («database is locked»).
- Автозагрузка: битые файлы уходят в карантин `_failed` (раньше один плохой
  файл навсегда останавливал очередь), файл, который ещё пишется, откладывается,
  одноимённые файлы не затирают архив, ошибки сети/JSON обрабатываются.
- Автозагрузка вынесена в отдельный поток — не подвешивает бота.
- Суммы из API больше не принимаются за цену за единицу (выручка не ×qty).
- Понятные разборы дат: ISO с миллисекундами и таймзоной, дд.мм.гггг, дд/мм/гггг.
- Числа «1 234,50» и «1,234.50» разбираются правильно.
- Кривые значения в .env не роняют запуск; validate() проверяет настройки
  автозагрузки и относительный DB_PATH.
- «Закупки» больше не перехватывают вопрос «сколько потратили на закупки».
